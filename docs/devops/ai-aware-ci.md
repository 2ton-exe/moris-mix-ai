### Deterministic AI quality gate

[Reusable Edge/API validation](../../.github/workflows/reusable-edge-api.yml) explicitly runs `ai_contracts_test.ts`, `ai_journeys_test.ts`, `eval_dataset_test.ts`, `gemini_adapter_test.ts`, `extract_recipe_test.ts`, and `generate_recipe_test.ts` alongside other backend tests. The required Deno command omits `--allow-net`, does not receive a production `GEMINI_API_KEY`, and uses mocked provider transport. It cannot serve as evidence of a successful live Gemini request.

The AI-owned [versioned dataset](../../supabase/functions/_shared/ai/eval_dataset.ts) is `2.1.1`; the [prompt file](../../supabase/functions/_shared/ai/prompts.ts) declares extraction `1.0.0` and Chef `1.1.0` at this checkpoint. Offline tests exercise real parsers, Zod schemas, error mappings, and explicit fixture expectations, not equality to a particular generated paragraph. They verify contracts and selected failure handling, **not** model accuracy, security against prompt injection, or the provider's real failure distribution. Dataset and prompt version bumps are a review/documentation convention, **not a separately enforced automatic version-bump gate**. The AI engineer owns prompts, fixture cases, and quality decisions; DevOps integrates and verifies their tests.

## Provider, secret, quota, and cost boundary

- Production provider requests originate in Supabase Edge Functions, not in the frontend or routine PR CI. The application uses server-side `GEMINI_API_KEY`, the Chef candidate-token secret `AI_CANDIDATE_TOKEN_SECRET`, and opt-in flags `AI_EXTRACT_ENABLED` / `AI_GENERATE_ENABLED`. Kill switches `AI_EXTRACT_DISABLED` and `AI_GENERATE_DISABLED` override those opt-ins. Record **names and roles only**, never values.
- The AI owner's [November 14–15 evaluation record](../ai-evaluation-report.md#dedicated-gemini-project-re-verification-2026-11-14) documents a dedicated Gemini project, an API-restricted key, and a separately authorized, cost-guarded live verification. The [restoration record](../ai-evaluation-report.md#production-restoration-verification-2026-11-15) reports that the production opt-ins were restored and extraction/Chef previews worked; do **not** confuse this later state with the earlier temporary kill-switch test. The November 27 audit below establishes secret-name presence and operator-attested key provenance, not current flag values.
- The backend has an application-level per-user daily `AI_DAILY_LIMIT` (default 20 logical operations), short-window controls, reservation/settlement behavior, bounded adapter retry, and stable failure responses; see [AI architecture](../ai-architecture.md) and [quota implementation](../../supabase/functions/_shared/ai/quota.ts). This is **not** an enforced project-wide Gemini monetary cap. A logical operation may contain more than one provider attempt due to retry.
- **2026-11-20 provider audit:** The original DevOps operator reviewed the existing Google Cloud project and AI Studio dashboards; dated, value-free findings and remaining gaps are recorded below. API-key restrictions or multiple keys within one project do not establish independent quota isolation, and an application-level quota is not a provider monetary cap. No secret values or private billing account data belong in GitHub.
- The separate hosted Supabase RLS test database is **not** proof of a separate Gemini evaluation project. Staging currently does not constitute independently configured Gemini-provider staging merely because a staging frontend exists.

### Unpaid-tier provider data-use boundary — 2026-11-20

The [Gemini API Additional Terms of Service](https://ai.google.dev/gemini-api/terms#unpaid-services) say that for **Unpaid Services**, including unpaid Gemini API quota, Google may use submitted prompts and responses for product improvement, and human reviewers may process that content. The terms caution against submitting sensitive, confidential, or personal information; regional terms may differ. The [Gemini pricing documentation](https://ai.google.dev/gemini-api/docs/pricing) also distinguishes Free-tier and Paid-tier data use.

The application sends user-authored **cooking notes** through Quick AI Entry and **pantry/preferences plus selected saved-recipe context** through AI Chef to an external model. Authentication, Supabase RLS, server-only keys, and redacted logs protect different boundaries; none overrides the provider's data-use terms. The November 27 operator attestation and configuration audit establish the Free-tier project association as described above; that provider policy is material to those submissions. The unresolved product-owner assessment below is not resolved by credential provenance.

**Use and regional eligibility — still unresolved:** The same [Gemini API terms](https://ai.google.dev/gemini-api/terms#use-restrictions) describe Google AI Studio and Gemini API as intended for developers building for **professional/business purposes**, not consumer use, and require **Paid Services** when making an API client available to users in the **European Economic Area, Switzerland, or the United Kingdom**. The terms also restrict API clients directed at or likely accessed by people under 18 (see [Age Requirements](https://ai.google.dev/gemini-api/terms#age-requirements)). A consumer-facing recipe application is not automatically established as prohibited simply because end users are home cooks; the intended use, audience, distribution, and applicable terms require an explicit product-owner assessment. The special EEA/CH/UK data-use treatment for unpaid quota does **not** by itself waive the Paid Services client-access requirement.

**Product/regional eligibility decision — OPEN (2026-11-20):** Mori's Mix targets home cooks (see [product definition](../../PRODUCT.md)) and exposes user-facing AI flows. This audit has **not verified** (1) the authorized professional/business developer-use rationale, (2) the intended/actual countries of access, (3) whether users under 18 are likely to access the AI features, or (4) regional/age eligibility restrictions enforced at the **server or service boundary**. The project's current Free tier is **not sufficient evidence** that public availability in EEA/CH/UK is permitted.

**Owner action before claiming provider eligibility:** The project manager/product owner, integration owner (Belen), and AI owner (Sioson) must document the intended audience, permitted regions and user-content policy, determine whether Paid Services or verifiable access restrictions are required, assign implementation of any necessary server-side controls, and record how those controls were checked. DevOps should record the approved outcome and project tier without independently inventing a policy or changing billing. Until this decision and any required controls are verified, **the provider-safety/eligibility review remains incomplete**, even if documentation CI passes. This guide does not establish compliance, disclosure, consent, or safe handling of real user content. Do not run tests using private customer content or link billing as an undocumented workaround.

### Live-provider smoke decision

**Decision reaffirmed 2026-11-27:** retain the existing *opt-in, human-authorized* live verification outside ordinary required CI; **defer an automated scheduled live-Gemini workflow**. The current Free-tier cost boundary is established by operator evidence, but evaluation is not quota-isolated, the key has no application restriction, other consumers are unknown, and product/eligibility review remains open. No new key/project, billing change or scheduled call is required for #162. Do not add the existing three-case `ai_extraction_live.ts` or model-discovery `ai_connectivity.ts` unchanged as a supposedly single-request scheduled smoke: retries and discovery may increase call count.

The [November 15 production report](../ai-evaluation-report.md#production-enablement-verification-2026-11-15) records one successful cost-guarded extraction and one Chef request, their request IDs, settled application quota, and the feature-flag sequence. Subsequent browser previews were separately observed. These **manual tests are not an automated scheduled smoke**, broad safety evaluation, reliability benchmark, or proof of a provider-wide spending cap. If a scheduled check is later authorized, it must be a separately scoped, synthetic, narrowly bounded, non-required workflow with a dedicated authorized key/project, explicit request/attempt ceiling, a safe skip/failure state, and no production release dependency. Any implementation needs its own review and execution evidence.
